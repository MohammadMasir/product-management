# Product & Order Management System

A backend-only Product & Order Management system built with Spring Boot, Spring Data JPA/Hibernate, Spring Security, and PostgreSQL. Supports two roles — `ADMIN` (product catalog management) and `USER` (browsing, cart, checkout) — with session-based authentication, layered architecture, DTOs, custom exceptions, global exception handling, and transactional order placement.

## Tech Stack

- **Java 21**, **Spring Boot**
- **Spring Data JPA / Hibernate**
- **Spring Security** (session-based auth, BCrypt password hashing)
- **PostgreSQL**
- **Maven** (wrapper included — `./mvnw`)
- **springdoc-openapi** (Swagger UI)

## Project Structure

```
com.interview.product_management
├── controller     # REST endpoints (Auth, Admin, Product, Cart)
├── service        # Business logic, transaction boundaries
├── repository     # Spring Data JPA repositories
├── model          # JPA entities
├── dto            # Request/response DTOs (records)
├── enums          # Role, ProductStatus, PaymentMode, PaymentStatus, DeliveryStatus
├── exceptions     # Custom exceptions + GlobalExceptionHandler
└── security       # SecurityConfig, CustomUserDetailsService
```

## Roles & Authentication

- Two roles: `USER` (default on signup via `/v1/api/auth/signup`) and `ADMIN` (created via `/v1/api/admin/signup`).
- Authentication is **session-based**, not token-based. `POST /login` authenticates and stores the security context in an HTTP session; the server responds with a `Set-Cookie: JSESSIONID=...` header. Every subsequent request must send that cookie back.
- Passwords are hashed with BCrypt. CSRF, form login, and HTTP Basic are all disabled — the only way to authenticate is via the login endpoints.
- Product-catalog management endpoints (`/v1/api/admin/product/**`) require the `ADMIN` authority. Cart and checkout endpoints require any authenticated user. Product browsing and auth endpoints are public.

## Getting Started

### Prerequisites

- JDK 21
- PostgreSQL running locally (or reachable) with a database created for this project
- Maven (or just use the included `./mvnw`)

### 1. Create the database

```bash
createdb product_management
```

### 2. Configure the datasource

Edit `src/main/resources/application.yaml` if your credentials differ from the defaults:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/product_management
    username: postgres
    password: root
  jpa:
    hibernate:
      ddl-auto: create-drop   # schema is (re)created on startup, dropped on shutdown
```

> `ddl-auto: create-drop` is convenient for development/evaluation since it builds the schema from the entities automatically, but it means data does **not** persist across restarts. Switch to `update` or `validate` (with a proper migration tool) for anything longer-lived.

### 3. Run

```bash
./mvnw spring-boot:run
```

The app starts on **`http://localhost:8080`**. Swagger UI is available at `http://localhost:8080/swagger-ui/index.html`.

## Database Schema

Six tables, generated by Hibernate from the entity mappings.

**users**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| email | varchar | unique, not null |
| password | varchar | BCrypt hash, not null |
| role | varchar(50) | `USER` \| `ADMIN`, default `USER` |
| created_at / updated_at | timestamp | |

**products**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| name | varchar | not null |
| price | numeric(10,2) | not null |
| quantity | integer | not null, check `>= 0` |
| product_status | varchar(50) | `ENABLE` \| `DISABLE`, default `DISABLE` |
| created_at / updated_at | timestamp | |

**cart**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| user_id | bigint | FK → users.id, unique (one cart per user) |
| created_at / updated_at | timestamp | |

**cart_items**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| cart_item | bigint | FK → products.id |
| cart_id | bigint | FK → cart.id |
| quantity | integer | not null, check `> 0`, default 1 |
| created_at / updated_at | timestamp | |

**orders**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| item_count | integer | not null, check `> 0` |
| total_quantity | integer | not null, check `> 0` |
| total_amount | numeric(10,2) | not null, check `> 0` |
| payment_mode | varchar(50) | `NONE`\|`UPI`\|`CASH_ON_DELIVERY`\|`CARD_PAYMENT` |
| delivery_status | varchar(50) | `PROCESSING`\|`OUT_FOR_DELIVERY`\|`DELIVERED`, default `PROCESSING` |
| payment_status | varchar(50) | `PENDING`\|`DONE`, default `PENDING` |
| users | bigint | FK → users.id |
| created_at / updated_at | timestamp | |

**order_items**
| Column | Type | Notes |
|---|---|---|
| id | bigint | PK |
| product | bigint | FK → products.id |
| orders | bigint | FK → orders.id |
| created_at / updated_at | timestamp | |

A user has exactly one cart (created automatically at signup). A cart has many cart_items. An order belongs to a user and has many order_items, each pointing at a product.

## API Endpoints

Base URL: `http://localhost:8080`

### Auth — public

| Method | Endpoint | Body | Description |
|---|---|---|---|
| POST | `/v1/api/auth/signup` | `RegisterDto` | Register a new `USER` |
| POST | `/v1/api/auth/login` | `LoginDto` | Log in, starts a session |

### Admin

| Method | Endpoint | Auth | Body | Description |
|---|---|---|---|---|
| POST | `/v1/api/admin/signup` | public | `RegisterDto` | Register a new `ADMIN` |
| POST | `/v1/api/admin/login` | public | `LoginDto` | Log in as admin |
| POST | `/v1/api/admin/product/add` | ADMIN | `ProductDto` | Add a product (defaults to `DISABLE`) |
| POST | `/v1/api/admin/product/{id}` | ADMIN | `ProductDto` | Update name/price/quantity |
| PUT | `/v1/api/admin/product/{id}/editStatus?productStatus=ENABLE` | ADMIN | — (query param) | Enable/disable a product |

### Products — public

| Method | Endpoint | Description |
|---|---|---|
| GET | `/v1/api/product` | List all `ENABLE`d products |
| GET | `/v1/api/product/{id}` | Get one `ENABLE`d product |

### Cart & Checkout — any authenticated user

| Method | Endpoint | Body | Description |
|---|---|---|---|
| GET | `/v1/api/cart` | — | View your cart + computed total |
| POST | `/v1/api/cart` | `CartItemsDto` | Add an item to your cart |
| PATCH | `/v1/api/cart` | `CartItemsDto` | Update an item's quantity; `quantity: 0` removes it |
| POST | `/v1/api/cart/checkout` | `OrderDto` | Place an order from your current cart |

## Sample API Requests

All examples use a cookie jar to carry the session between calls.

**1. Register and log in as ADMIN**
```bash
curl -X POST http://localhost:8080/v1/api/admin/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"admin1234","confirmPassword":"admin1234"}'

curl -c admin_cookies.txt -X POST http://localhost:8080/v1/api/admin/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"admin1234"}'
```

**2. Add a product and enable it**
```bash
curl -b admin_cookies.txt -X POST http://localhost:8080/v1/api/admin/product/add \
  -H "Content-Type: application/json" \
  -d '{"name":"Wireless Mouse","price":19.99,"quantity":50,"productStatus":"ENABLE"}'

# or add first, enable after (id is returned in a real DB — check via GET /v1/api/product)
curl -b admin_cookies.txt -X PUT "http://localhost:8080/v1/api/admin/product/1/editStatus?productStatus=ENABLE"
```

**3. Register and log in as USER**
```bash
curl -X POST http://localhost:8080/v1/api/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"user1234","confirmPassword":"user1234"}'

curl -c user_cookies.txt -X POST http://localhost:8080/v1/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"user1234"}'
```

**4. Browse products**
```bash
curl http://localhost:8080/v1/api/product
```
```json
[
  { "id": 1, "name": "Wireless Mouse", "price": 19.99, "quantity": 50 }
]
```

**5. Add to cart**

> `id` is required by validation even though it's unused for a new item — send `0`.

```bash
curl -b user_cookies.txt -X POST http://localhost:8080/v1/api/cart \
  -H "Content-Type: application/json" \
  -d '{"id":0,"productId":1,"quantity":2}'
```

**6. View cart**
```bash
curl -b user_cookies.txt http://localhost:8080/v1/api/cart
```
```json
{
  "cartItems": [{ "id": 5, "productId": 1, "quantity": 2 }],
  "totalAmount": 39.98
}
```

**7. Update cart item quantity (or remove with `quantity: 0`)**
```bash
curl -b user_cookies.txt -X PATCH http://localhost:8080/v1/api/cart \
  -H "Content-Type: application/json" \
  -d '{"id":5,"productId":1,"quantity":3}'
```

**8. Checkout**
```bash
curl -b user_cookies.txt -X POST http://localhost:8080/v1/api/cart/checkout \
  -H "Content-Type: application/json" \
  -d '{"paymentMode":"UPI","paymentStatus":"PENDING","deliveryStatus":"PROCESSING"}'
```
```json
{
  "id": 10,
  "cartProductDetailsDtoList": [{ "productName": "Wireless Mouse", "quantity": 3 }],
  "itemCount": 1,
  "totalAmount": 59.97,
  "paymentMode": "UPI",
  "deliveryStatus": "PROCESSING",
  "paymentStatus": "PENDING"
}
```

**9. Example error response** (e.g. insufficient stock)
```json
{
  "time": "2026-09-09T10:15:30",
  "status": "400",
  "message": "Insufficient quantity, Only 2 remaining."
}
```

## Business Rules

- **Stock is server-authoritative.** The cart total, order item count, and the products actually purchased are all computed from what's persisted in `cart_items` at checkout time — never trusted from the client.
- **Order placement is transactional.** If any item in the cart has insufficient stock, the entire order — and any stock already deducted for earlier items in the same checkout — is rolled back. Nothing is partially persisted.
- **Checkout on an empty cart is rejected** with a `400 Bad Request` before any order is created.
- **A product must be `ENABLE`d to be visible or purchasable.** Newly added products default to `DISABLE` until an admin explicitly enables them; disabled products are excluded from both listings and checkout.
- **The cart is cleared automatically** after a successful checkout.

## Error Response Format

Validation errors (`400`) return a map of field/object → message. All other handled exceptions (not found, insufficient stock, out of stock, bad auth, etc.) return:
```json
{ "time": "...", "status": "...", "message": "..." }
```
